## Delivered scope

### Subscriptions, notifications, and dynamic registry

The modern `subscriptions/listen` request is routed to an HTTP SSE stream with an acknowledgement first, request-ID correlation, filter negotiation, and owner-bound lifetime. Typed HTTP client methods decode resource-updated and tool/resource/prompt-list-changed notifications. The runtime and HTTP server expose resource/list notifications and live tool registration/removal. Accepted tool changes update the authoritative server used for subsequent listing and dispatch, update open stream runtimes, and emit the tools-list notification. Duplicate removals do not emit a false change. The integration test registers a tool while a subscription is open, observes the change notification, lists and calls the tool through a second HTTP connection, unregisters it, observes the second notification, and verifies it is gone.

### Protocol and typed clients

The frozen schema corpus now covers the subscription request, acknowledgement, resource-updated notification, and the three list-change notifications using the actual encoder output. Annotation declarations and private zero-TTL cache metadata remain present and the schema gate enforces the cache contract for the delivered families.

The HTTP typed client now also traverses resource, resource-template, and prompt listing pages. Discovery, tool listing/calls, resource reads, prompt gets, completions, and the subscription stream share a checked HTTP request path. `connect_with_ca` allows a caller-specified trust root; a local CA-signed peer test proves default trust rejects its certificate and explicit CA trust succeeds.

The stdio client launches the configured executable directly with an argument list, owns the port through a monitored actor, bounds line frames and full responses, applies per-request deadlines, correlates string response IDs, skips valid no-ID notifications while waiting, and returns an error for unrelated response IDs. Closing the client cancels an in-flight wait and closes the child; shutdown acknowledgements use a process monitor, so repeated or concurrent close and an already-dead owner do not panic. Existing typed calls, discovery, reads, lists, prompt gets, and completions route through the same client API over stdio. Typed `subscriptions/listen` and a stdio notification reader are not implemented.

The interrupted Erlang boundary also received two correctness fixes: the unsupported `lists:filter_map` call was replaced with `lists:filtermap`, and an unsafe catch binding was corrected. The stdio launcher resolves the executable and starts it with `spawn_executable`, not a shell fallback.

Example delivered calls:

```gleam
let assert Ok(client) = relay_client.connect_with_ca(config, "test/fixtures/tls/root-ca.crt")
let assert Ok(resources) = relay_client.list_resources(client)
let assert Ok(subscription) = relay_client.listen(client, requested_notifications)
let notification = relay_client.next_notification(subscription, 1000)
```

For local subprocesses, `connect_stdio` accepts an executable plus explicit arguments; supported typed request methods use the same client surface. The subscription example above currently applies to HTTP only.

## Wave 3 review repair evidence

The subscription-establishment blockers from the independent Wave 3 reviews are repaired in the dirty tree. `subscriptions/listen` now honors the tool list-change filter whenever the server supports the live tool registry, including an initially empty registry. The HTTP hub returns the immutable current tool values and a bounded generation with each request snapshot. Registration compares generations inside the serialized hub actor; when the generation changed, it unregisters every snapshot tool and registers every current tool before acknowledging. This full reconciliation preserves same-name replacement handler and metadata changes without retaining a lifetime change journal or historical `ContextTool` closures.

The SSE broker holds all initial frames for `subscriptions/listen`, including the acknowledgement, until the hub returns a successful registration result. A timeout, dead hub, failed reconciliation, or writer failure therefore cannot expose an acknowledged ghost stream. A successful registration releases the bounded initial frame buffer in order; cleanup sends an unregister message when admission may have succeeded and then stops the runtime, writer, and broker.

Deterministic regressions in `test/relay/client_test.gleam` hold the request's context callback at the runtime admission boundary, issue `register_tool` while that callback is blocked, release the callback, and then assert all of the following: the acknowledgement retains `toolsListChanged: true`; the open stream emits `ToolsListChanged`; and a subsequent `list_tools` request sees the registered tool. The same test helper runs for both an empty registry and a populated registry.
